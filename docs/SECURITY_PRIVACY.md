# Security and privacy — implemented 0.2 behavior

Main executable requests `asInvoker`; there is no self-elevation, service, driver or startup task. Native P/Invoke calls read IP Helper and WLAN metadata only. Native buffers are bounded and freed, retry counts are finite. Process start time prevents the UI from presenting a bare PID as a stable process instance, but long-term executable grouping is not implemented.

Passive startup does not send network probes or contact a backend. DNS/ICMP and HTTPS transfer testing require explicit user action. Transfer testing sends generated random data to the displayed endpoint, uses HTTPS without credentials/cookies, rejects redirects and limits payload size and time. It does not call provider result-logging endpoints. HTTP upload rates use the submitted body size, not independent receiver-side measurement; this limit is disclosed in the guide.

Live address and SSID visibility are opt-in. Process names can be hidden. No payload, password, browser content, executable path, remote destination, MAC or BSSID collection is implemented. The database retains adapter IDs/names/types, aggregate counters and state transitions. Diagnostic targets are redacted from stored/exported results unless address collection is enabled; explicitly configured target settings remain stored for convenience.

CSV exports quote cells and prefix formula-like strings to avoid spreadsheet formula execution. SQL values are parameterized. Retention validates bounds, deletes bounded batches and avoids UI-thread work. A newest-only UI snapshot slot prevents an unbounded dispatcher backlog; session totals are accumulated by the collector worker so dropping chart updates does not drop counted bytes.

Warning/error logs are local and rotate at about 1 MiB with one previous file. Current collection/storage logs use exception type rather than network addresses or raw payloads. Startup exception logs can include source paths; review before sharing. SQLite files use normal per-user filesystem protection, not application-level encryption. No stored credentials are required.

## Optional elevated collector and IPC (scaffold)

`NetworkIntelligence.MonitoringService` is a separate, optional, explicitly installed process. It is never started by the main app, never installed automatically, and the main app runs fully without it — the only capability it unlocks is per-application byte accounting (still not accuracy-certified; see `docs/ETW_VALIDATION.md`). It reads only kernel Network ETW event headers (owning PID, transfer size, protocol, direction, address family); it never reads packet payload, and it makes no firewall, DNS, driver or startup-task changes.

IPC is a named pipe (`NetworkIntelligence.MonitoringService.v1`), authorized by the OS at connect time via a pipe ACL that allows only Administrators and interactively logged-on local users, and explicitly denies anonymous and network logons — the service never accepts a remote connection. There is no free-form command channel: every message is one of a fixed, versioned `ServiceMessageType` (`Hello`/`HelloAck`/`SnapshotRequest`/`SnapshotResponse`/`Error`), length-prefixed and capped (4 KiB requests, 1 MiB responses; a declared length outside that bound is rejected before any body is read). The connecting client's Windows identity is resolved and logged for audit after the first message (Windows requires a prior read before impersonation info is available); this logging is best-effort, not the security boundary — the pipe ACL is. Manually validated end to end: an elevated service instance, an unelevated client on the same machine, real per-process byte attribution served over the pipe, zero events lost.

Install is manual and explicit (`scripts/service-install.ps1`, elevated), registers `StartupType Manual` (it does not run automatically, does not start with Windows, and installing it does not start it), and is fully removable (`scripts/service-uninstall.ps1`) without affecting the main app. Service logs are local, rotate at ~2 MiB, and live under `%ProgramData%\NetworkIntelligence\Service` (the service runs outside any single user's session, so it cannot use a per-user AppData path).

Remaining gates before this is production-ready: code signing, a least-privileged dedicated service account (the scaffold currently runs under whatever elevated account starts it — production should not default to LocalSystem without justification), unauthorized-client access testing, and the accuracy/overhead validation items listed in `docs/ETW_VALIDATION.md`. Unsigned portable packaging, unavailable dependency auditing, untested public endpoint behavior, UI automation coverage and Windows 10 compatibility remain separate release limitations.
