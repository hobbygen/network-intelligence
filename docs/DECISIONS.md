# Architecture decision records

## ADR-001 — Native WinUI / .NET 10 (approved)

Keep the requested native stack. Installed SDK is 10.0.400. Windows App SDK 1.8.260804001 restored from cache and passed Debug/Release build and blank-window launch checks. Security audit and release support review remain pending. A WinForms or browser UI is not an implicit substitute. Proposed API floor: Windows 10 1809; supported editions and tested minimum remain separate release conditions.

## ADR-002 — Tiered, quality-bearing telemetry (approved)

Adapter counters are the first tier. Connection ownership is metadata, never a byte proxy. ETW must pass controlled traffic validation before per-application usage is enabled. Decreased counters or long gaps produce unavailable intervals, not guessed rollover values. Process identity includes creation time. Elevated service is optional and deferred until technically justified.

## ADR-003 — Local SQLite and bounded retention (approved)

Use explicit transactional migrations and a single background writer. Default one-year retained aggregates. Keep live high-frequency samples bounded. Export source/state alongside values. Privacy controls act before persistence and export, not just on UI rendering.

## ADR-004 — Phase gate (required by project brief)

Sections 4.1, 15 and 21 require architecture/telemetry validation. The owner explicitly approved the proposed architecture and proceeding on 2026-09-17. Core adapter monitoring has proceeded with validated APIs. Per-application byte accounting remains gated on accuracy evidence; owner approval does not substitute for measurement validation. No production-readiness claim.

## ADR-005 — Portable engineering distribution (accepted for early access)

Publish a self-contained x64 folder/ZIP for the first usable build. This can run outside the IDE without installing a privileged component. It is not a signed production installer; MSIX/signing and clean-machine deployment tests remain required for 1.0.

## ADR-006 — ETW kernel Network provider validated as the Tier-3 mechanism (accepted)

Standard-user and elevated experiments both ran (see `docs/ETW_VALIDATION.md`). Standard user: `TraceEventSession.IsElevated()` false, no session attempted, `PermissionDenied` — confirms Tier 2 exact byte accounting is unavailable without elevation. Elevated: a real-time session on `Microsoft-Windows-Kernel-Network` (`NetworkTCPIP` keyword), consumed via `Microsoft.Diagnostics.Tracing.TraceEvent`, ran 30 seconds with zero events lost and produced real per-process send/receive byte totals across 15 processes, IPv4 and IPv6, reading only event headers — never payload. This is the validated Tier-3 mechanism. It is not yet an accuracy-certified feature: controlled known-byte comparison, process-restart attribution, adapter disambiguation, and overhead benchmarking (validation-plan experiments 5–6) remain outstanding before the Application Usage page can claim byte-level accounting. The mechanism must ship only inside the optional, explicitly-installed, least-privileged `MonitoringService` (section 5.2) with authenticated local IPC to the unelevated main app — never by elevating the main app itself. `Microsoft.Diagnostics.Tracing.TraceEvent` is added only to the isolated `tools/NetworkIntelligence.TelemetryProbe` project pending this validation; it must be re-evaluated as a production dependency (signing, servicing, size) before it is referenced from the service.

## ADR-007 — MonitoringService scaffold: Generic Host worker, named pipe IPC (accepted)

`NetworkIntelligence.MonitoringService` is a .NET Generic Host worker (`Microsoft.Extensions.Hosting.WindowsServices`), so the same binary runs as an ordinary elevated console process for local testing (`scripts/service-run-foreground.ps1`) or as a registered Windows Service (`scripts/service-install.ps1`/`service-uninstall.ps1`, `StartupType Manual`, never installed or started automatically). `EtwCollector` promotes the validated ADR-006 mechanism into a continuous `BackgroundService`: a persistent kernel Network ETW session aggregated into fixed 5-second windows, exposed as the latest immutable `ServiceSnapshot`. `PipeServer` serves that snapshot over a named pipe (`NetworkIntelligence.MonitoringService.v1`) to unelevated local clients.

IPC design, per section 13.4: a `PipeSecurity` ACL (Administrators + `WellKnownSidType.InteractiveSid`, explicit deny on `AnonymousSid`/`NetworkSid`) is the actual authorization boundary, enforced by the OS before the server code runs — never a network-reachable pipe. Messages are a fixed, versioned envelope (`ServiceMessageType` enum: Hello/HelloAck/SnapshotRequest/SnapshotResponse/Error) with length-prefixed JSON framing and a hard size cap (`ServiceWireFormat`, `NetworkIntelligence.Contracts`) — never a free-form command string. Client identity is resolved via `GetImpersonationUserName()` after the first read (required by the Windows API) purely for audit logging; a failure to resolve it does not itself deny an already-ACL-authorized connection. All of this was validated end to end manually: an elevated service instance served real per-process byte data, zero events lost, to a client running as the interactively logged-on standard user, with the client's identity correctly logged.

Deferred to a later ADR: code signing, a dedicated least-privileged service account (the scaffold runs under whatever elevated account starts it), and wiring a client into the main App/Infrastructure (the scaffold's only client today is `tools/NetworkIntelligence.TelemetryProbe --service-status`, kept deliberately separate so the WinUI app's Tier 1/2 behavior is untouched by this work).

## ADR-008 — Controlled-traffic accuracy: exact match on loopback, still narrow (accepted)

`tools/NetworkIntelligence.TelemetryProbe --accuracy-test-mib N` sent an exact, independently-tallied N MiB over a loopback TCP socket and compared it against the MonitoringService's ETW-attributed total for the same PID (see `docs/ETW_ACCURACY.md`). Both required sizes (1 MiB, 100 MiB) matched byte-for-byte in both directions, zero events lost. This is a real, strong result but a narrow one: loopback only, single process, single short-lived high-throughput TCP connection. It raises confidence in the mechanism without being a general accuracy certification — concurrent processes, process restart, real/physical adapters, UDP-against-reference, and low-rate/long-duration behavior (the rest of validation-plan experiments 5–6) remain open before requirements section 7.4's gate is satisfied.

## ADR-009 — Wire the MonitoringService client into the App, gated and degrading (accepted)

Adds `IApplicationTrafficClient`/`MonitoringServiceClient` (`NetworkIntelligence.Infrastructure`) — a short-lived, reconnect-per-call named-pipe client, matching the probe's already-validated protocol usage. `NetworkIntelligence.Application.MonitoringService` polls it on its own independent 4-second `PeriodicTimer`, deliberately decoupled from the 2-second adapter-collection loop, so a slow or unreachable optional service can never delay adapter monitoring or history writes; failures surface as an `Unavailable` `ServiceSnapshot`, never an exception. The Application Usage page gained a "Live per-application bandwidth (optional)" card bound to this data, with the existing socket-ownership list kept unchanged below it — the InfoBar was reworded from "ETW validation is required" (no longer true) to explain the feature is off by default, requires manually installing the separate service, and is only accuracy-validated for a single loopback connection (ADR-008), not certified for general use.

Verified visually end to end via the app's `--smoke-test --smoke-page <name>` flag (extended in this change to pick which page renders, since Application Usage isn't the default landing page): with no service running, the card renders "Unavailable · Monitoring service not reachable" and the rest of the page works normally; with the service running elevated, the card renders real live per-process rates (e.g. curl.exe traffic at ~3.2 Mbps, `0 events lost`, correct window timestamps) sourced through the same pipe validated in ADR-007/ADR-008. This is UI wiring, not a claim of general accuracy or a promotion of Application Usage to "fully implemented" per requirements section 7.4 — persisted history, baselines, anomaly detection, and trust/exclusion controls (spec sections 10.2–10.6) remain unbuilt.

## ADR-010 — Persist per-application traffic as minute aggregates, schema version 2 (accepted)

Extends `SqliteHistoryStore` to a proper incremental migration (a v1 database gets only the v2 delta applied, not a v1 re-run) adding `ApplicationTrafficMinutes`, keyed by `(Pid, ProcessName, Minute)` — the same "aggregate into minute buckets, not raw samples" pattern `TrafficMinutes` already uses for adapters, chosen for the same reason: storing every 5-second `MonitoringService` window uncapped would scale to tens of millions of rows/year at default retention (see `docs/DATABASE_SCHEMA.md`). `IHistoryStore.SaveApplicationTrafficAsync` is a deliberate no-op unless the snapshot's `Availability` is exactly `"Measured"` — an unreachable service persists nothing, never a fabricated zero-byte row. Wired into `NetworkIntelligence.Application.MonitoringService`'s existing 4-second application-traffic poll (ADR-009), and into the same retention/deletion/export code paths adapter history already uses (`ExportService.WriteApplicationUsageAsync` mirrors `WriteUsageAsync`).

Grouping by (Pid, ProcessName) is **not a stable application identity** — this is the same PID-reuse caveat already disclosed for the live view, now also true of stored history, and is documented as such everywhere it's surfaced (schema doc, export payload, UI caption). Stable identity resolution (grouping by normalized executable identity, handling restarts) is deferred to the baseline/anomaly-detection work (spec Phase 7), which needs this stored history to exist first. Covered by 4 new xUnit tests (aggregation across saves, unavailable-snapshot no-op, retention/deletion parity with adapter history, export round-trip); not yet covered by a long-duration/high-volume test (validation-plan experiment 6).

## ADR-011 — Algorithmic anomaly detection: process-name baselines, Welford + trim, sustained+cooldown (accepted)

Implements requirements section 10.3–10.6's detection pipeline as three deliberately separated layers, matching the codebase's existing pattern of keeping algorithmic logic pure and testable:

1. **`NetworkIntelligence.Domain.BaselineCalculator`** (pure): computes a per-process-name `ApplicationBaseline` — mean and standard deviation of download/upload rate, separately — from stored `ApplicationTrafficMinutes` history. Uses Welford's online algorithm, then one outlier-trimmed re-pass excluding samples beyond 4 standard deviations of the first pass ("robustly limit anomalous samples entering baseline," `ARCHITECTURE_REVIEW.md`). This is a **deliberate simplification**, not the richer rolling-median/MAD/percentile-envelope statistic that document's anomaly section originally sketched as a proposal — chosen because it is simple, exact, and fully unit-testable, at the cost of being less robust to sustained (non-brief) outlier periods than a median-based approach would be. Revisiting this is the natural next step if live use shows it under- or over-fires.
2. **`NetworkIntelligence.Domain.AnomalyEvaluator`** (pure): a momentary, stateless per-direction comparison against the baseline, gated by minimum sample count, minimum observation days, and a minimum absolute bandwidth floor (so a near-idle baseline can't turn a trivial byte count into an extreme deviation multiple) before it will ever return `Anomalous` — matching "new applications must have a learning period" and "do not trigger alerts for every short-lived spike" (requirements section 10.4). Explanation text is worded as an explicit disclaimer ("not a malware or security determination"), satisfying "never state that the application is malicious based only on bandwidth" (section 10.6) by disclaiming rather than merely omitting the topic.
3. **`NetworkIntelligence.Application.AnomalyTracker`** (stateful, but clock-injected for determinism): turns a stream of momentary verdicts into a fire/no-fire decision, requiring continuous `Anomalous` verdicts for a minimum sustained duration (default 30s) before firing, then a per-(process,direction) cooldown (default 15 minutes) before firing again. Dropping below threshold resets the sustained timer — a brief spike never accumulates toward firing.

**Defaults** (`AnomalySettings.Balanced`: 60 samples, 7 days, 50 KB/s floor, 3.0 standard deviations, 30s sustained, 15min cooldown) are the provisional parameters `ARCHITECTURE_REVIEW.md` proposed for false-positive testing — **not validated against a real false-positive rate**. That validation needs days-to-weeks of live usage data across varied applications and is explicitly out of scope for this change; `docs/VALIDATION_PLAN.md` tracks it as outstanding. Sensitivity (the standard-deviation multiple) is user-configurable in Settings; the other parameters are not yet exposed.

**Orchestration**: `NetworkIntelligence.Application.AnomalyDetectionService` is a pure downstream consumer of `MonitoringService.ApplicationTraffic` (ADR-009) — it never touches ETW or the pipe directly. It refreshes baselines from a 30-day lookback at most once every 2 minutes (bounding database load), evaluates every live sample against the cached baseline, and on a fired anomaly persists an `AnomalyEvent` row (schema version 3, `AnomalyEvents` table) before raising an event for the UI. Quiet hours and the alerts-enabled setting gate the *notification* only — the row is always written, satisfying "quiet hours suppress notifications, not evidence storage" (section 12.6) — by deciding the `Notified` flag once at write time rather than mutating it later. `QuietHours.IsQuiet`, previously private to `MainWindow`, was promoted to a shared `NetworkIntelligence.Application` helper so both the adapter-disconnect and anomaly notification paths use one implementation.

**Identity**: baselines and evaluation key on process name alone (not `(Pid, ProcessName)` like the raw storage in ADR-010) — multiple concurrent PIDs sharing a name (e.g. several `chrome.exe` helpers) are summed into one learned baseline, matching "multiple processes belonging to one application" (section 10.1). This still is not a stable identity: a short-lived process that had already exited by the time its window closed is named `Process {pid} (exited)` by `EtwCollector`, which embeds the PID and so never accumulates baseline history across restarts — safe (such processes simply stay in permanent "insufficient history"), but means restart-prone short-lived processes will likely never be evaluated. Fixing that requires the stable-identity work already flagged as deferred in ADR-010.

**UI**: a "Live per-application bandwidth" trust button (writes `AppSettings.TrustedApplications`, checked case-insensitively and short-circuits evaluation entirely), a Dashboard "Recent alerts" card, and a Settings card for the enable toggle, sensitivity, and the trusted-application list (view-only there; untrust is not yet implemented). Snooze (as distinct from dismiss) from section 10.6's alert-action list is not implemented in this pass.

**Testing**: 24 new Domain/Application-layer unit tests (29 total including storage) covering the required scenarios from section 16.4 — normal traffic, sustained spike (direction-specific), new application, insufficient history, trusted application, below-bandwidth-floor, brief-spike-never-fires, cooldown, sustained-timer-reset-on-dip, independent per-(process,direction) tracking, and quiet-hours gating (overnight wrap, same-day range, always-quiet) — plus 5 storage/settings tests (multi-PID minute-series grouping, anomaly persistence/ordering, retention/deletion parity, sensitivity bounds). 61 tests total, all passing. Verified against a real elevated `MonitoringService` run: the ingestion pipeline processed live traffic data without error and correctly produced zero fired anomalies (no baseline yet exists for a fresh database — exactly the intended "new application" safe state), confirmed by direct database inspection.

## ADR-012 — Resolve `EtwCollector` process names from kernel Process events, not a post-hoc live lookup (accepted)

Fixes the restart-attribution gap ADR-011 flagged as deferred: `EtwCollector.ToSample` previously resolved a window's process name by calling `Process.GetProcessById(pid)` at *window-flush* time — up to `WindowDuration` (5s) after the traffic occurred. Any process that had already exited by then fell back to `"Process {pid} (exited)"`, a name that embeds the PID and so is different on every restart. Since baselines and anomaly evaluation key on process name alone (ADR-011), a restart-prone short-lived process (e.g. an updater helper that spawns, does a small amount of network I/O, and exits every few seconds) could never accumulate the 60-sample/7-day learning period under one name — it was permanently stuck in "insufficient history," silently exempt from detection.

**Fix**: `EtwCollector` now additionally enables the kernel **Process** ETW provider (`KernelTraceEventParser.Keywords.Process`) alongside the existing NetworkTCPIP provider — no new privilege requirement, both already need elevation. It maintains a `ConcurrentDictionary<int, ProcessNameEntry>` populated from `ProcessStart` (a process spawning during the session) and `ProcessDCStart` (the rundown of processes already running when the session starts), so a name is captured at or near the process's actual start — not raced against its exit. Window flush now resolves through this table first, falling back to a live `Process.GetProcessById` only for the rare case where neither event has been observed yet, and to the PID-embedded placeholder only if both fail. `ProcessStop` marks an entry's stop time rather than removing it immediately, so a window that has not flushed yet can still resolve a process that exited mid-window; entries are pruned 2 minutes after their stop time on each window flush, bounding the table under long-running process churn (spec section 14) without needing the name at the exact instant of exit. `ProcessDCStop` (the mirror rundown at session end) is deliberately not subscribed — it only fires during the service's own shutdown, after the flush loop has already exited.

**Still not a fully stable identity**: this fixes name *loss*, not the underlying PID-reuse caveat already documented in ADR-010/011 — two different process instances that both use the same PID within one 5-second window still merge into one sample, and identity is still process name, not `(name, start time)` or executable path.

**Live-validated**: run elevated via `scripts/service-run-foreground.ps1` with both kernel keywords enabled — session started cleanly (no provider-enable error), 0 events lost. Spawned 15 concurrent `curl.exe` processes against a real HTTPS endpoint, each completing in roughly 1–2 seconds — short enough that, under the pre-fix code, `Process.GetProcessById` at the next window flush would very plausibly have raced their exit. Polled live via `TelemetryProbe --service-status` from a non-elevated shell: `curl` was attributed by its real name, never as a `Process {pid} (exited)` placeholder. This confirms the specific failure mode ADR-012 targets — short-lived process name loss — is fixed; it does not by itself confirm the full downstream effect of a restart-prone process accumulating a baseline over many separate windows (that behavior follows mechanically once the name is stable, and was already covered by ADR-011's baseline tests, but wasn't separately re-verified here).
